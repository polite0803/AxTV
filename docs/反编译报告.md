### 失败的 204 处

jadx 的方法级失败集中在混淆最狠的 Compose UI 类（`on5` / `eu5` / `ro5` 等），表现为：
- 方法体被替换为 jadx 的 `// JADX WARN` / `Code duplicated` / 抛 `UnsupportedOperationException` 之类占位
- **方法签名、调用关系、常量、字符串仍然完整**，所以"这个 App 有什么功能"不受影响；
  个别函数的内部算法细节需要回到 smali 级确认（必要时用 `baksmali`/`jadx --export-gradle` 对照）

### 原生库结论

`lib/arm64-v8a/libquickjs-android-wrapper.so`（1.3 MB）等 8 个 `.so` **不含应用自有逻辑**：

- 导出符号只有 `Java_com_whl_quickjs_wrapper_QuickJSContext_*` 与
  `Java_com_whl_quickjs_android_QuickJSLoader_*`，即开源库
  [`quickjs-android`](https://github.com/wanghb2018/quickjs-android)（com.whl.quickjs）的 JNI 包装
- `libandroidx.graphics.path.so` 是 AndroidX 的路径插值库
- 抖音签名算法（a_bogus / X-Bogus）全部在 **JS**（`assets/abogus.js`、`bdms.js`、`abogus_dy.js`、`sign.js`）
  里，由这个 QuickJS 执行，**不在 Native 层**

因此 Ghidra 的用途仅限"确认没有藏 Native 逻辑"，**不是本次反编译的必需环节**。

> 实测：`analyzeHeadless` 对该库做全量自动分析（import → ANALYZING all memory and code →
> decompile）耗时极长且把机器压满，在 4 核 `-max-cpu` 下跑到 decompile 阶段仍未结束，
> 已中止并删除半成品工程。需要看反汇编时再单独用 GUI 打开，不要和反编译/重构并行跑。
