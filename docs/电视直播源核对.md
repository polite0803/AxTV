## 2. 排位依据

- **vbskycn / TianmuTNT 靠前**：央视、卫视流多可连，TianmuTNT 抽检 10/10 全连。
- **iptv-org `cn.m3u` 居中**：CDN 托管，条目规范但含境外主机，抽检 7/10。
- **iptv-org `streams/cn.m3u` 靠后**：广度兜底，含海外与已失效主机，抽检 3/10——只在前面的源给不出某频道时才用得上。
- **suxuang 垫底**：条目最多（1273，地方台丰富），但**央视主机 `101.35.240.114:88` 已 404**。若把它排前，会出现「大频道全挂、小台能播」的假象。

## 4. 口径与已知边界

- **条目数 ≠ 可频道数**：`ESTIMATED_CHANNEL_COUNTS` 是 m3u 里的总行数；实际进入 UI 的频道数由 `ChannelCatalog` 按 D3 名称归一（去空白 / 全半角 / 大小写）聚合后再分组，且受各源 `group-title` 覆盖率影响，因此**电视上看到的频道数会小于本表条目数**。
- **抽检可连数是保守活性读数，不是全量统计**（`REALTV_COVERAGE` 注释已声明）。样本量各源不同（20 / 10 / 10 / 10 / 见注释），不得当作百分比分母使用。
- **`suxuang` 的 17** 与其余四项口径不完全一致（其余为「抽检 N 条中可连 M 条」，它记录的是可连计数），引用时以代码注释为准。
- 不做的事：不伪造 Referer/UA 破解访问控制、不自建转播或二次分发（红线见 PLAN §7 与 BuiltInSources 头部）。

## 5. 重测口径（要更新本表时按这个走）

1. 按生产客户端请求头拉每份 m3u（Accept-only，不带浏览器 UA 伪装），记录 HTTP 码与解析后条目数。
2. 每源固定样本量抽样请求**分片 URL**（不是 m3u 地址本身），记录可连数；样本量写进本文与代码注释，两处必须一致。
3. 若某源大频道集中失败而小频道正常 → 先查该源主机是否 404（suxuang 案例），再决定是否降序或剔除。
4. 五个源全部失败时 → 先查共同解析路径（DNS / 出口），不要直接判定源集体失效。
5. 改完 `BuiltInSources` 后需同步：`VERIFICATION_DATES`、`ESTIMATED_CHANNEL_COUNTS`、`REALTV_COVERAGE`、`URLS` 注释、本文 §1–§3。
